# Annotate Review Flow

jj-restack-pr・sentinel・review-verdict・annotate・review-comment・create-pr はそれぞれ独立したスキル。実行は各スキルに従う。ここではこれらを繋ぐ順序と、繋いだときだけ生まれる判断だけを書く。

## フロー(この順で)

0. **`gh pr checkout <番号>` で対象PRをcheckoutし、差分を用意する。** 同名ブランチが古くても最新のheadへ更新されるため。sentinelの既定はローカルの未コミット差分なので、PRの差分は annotate スキルの「モードA → A2. 対象の決定」の手順（GitHubの「Files changed」と同じ基準）で取り、対象として明示して渡す。

1. **兄弟PR（同じbaseから並行分岐した未マージPR等）の有無をユーザーに確認する。** 決めつけない。あれば差分と既存のレビュー・議論を取得する（量が多ければサブエージェントに委譲してよい）。差分はsentinelに比較対象として評価させ、判定側にも渡す。兄弟PRは指摘を作る根拠にも退ける根拠にもなる。レビュー履歴はステップ6の解説アノテーションの判断材料にする。

2. **jj-restack-pr をサブエージェントに委譲し、PR差分を review 単位の change に積み直させる。** ステップ5までと並行して走らせる（積み直しは差分の中身を変えない）。作業場所は `jj workspace add` で切ったリポジトリ外の別ワークスペース。同じディレクトリだと中間状態の作業ツリーをsentinelや判定の委譲先が読んでしまうため。

   この流れ固有の差分:

   - モードは読み順（前提から順に 1 つずつ読んで詰まらないよう並べるモード。change 数は気にしない）。ユーザーが「最小構成で」と言ったときだけ最小構成（同じ変更を最も少ない change に整理するモード）
   - **jj-restack-pr Phase 7 の `git checkout` はやらせない**（元の作業ディレクトリ＝ステップ0でPRをcheckoutした場所。そのHEADはステップ0のまま）。bookmark（jj のブランチ。名前は `<元のブランチ名>-splitted`）を付けたら `jj git export` まで進ませる（しないと元の作業ディレクトリから積み直したブランチが見えない）
   - 完了報告は change ごとに change-id・commit id・タイトル・対象path（ステップ6でアノテーションを付ける commit を決めるのに使う）
   - **承認・連絡待ちで止まらせない**。分岐は次の既定で決めさせ、決めた内容を完了報告に書かせる
     - jj-restack-pr Phase 2 のプラン承認・検証失敗後の再承認は取らない
     - jj repo でなければ元の作業ディレクトリを colocate 化する（git リポジトリに `.jj` を足して jj を併用できる状態にする。`rm -rf .jj` で戻せる）
     - 1 ファイルに複数の change の変更が混在していたら、jj-restack-pr の三択のうち (a) 最終状態から中間状態を手で作って積む
     - 検証コマンドが規約から見つからなければ change ごとの検証を飛ばす（積み直し前後の内容一致の検証は飛ばさない）

   積み直しが成立しない場合（change が1つにしかならない・fork PR等）や途中で失敗した場合は待たずに進め、ステップ6は元のPR headに付ける。

3. **sentinelで指摘を洗い出す。** IMPORTANT: 使うのは並列レビューの集約までで、集約結果はそのままステップ4に渡す。フェーズ3（突き合わせ）・3.5（先行修正）・4（auq-web）は使わない。裏取りはステップ4の委譲先に寄せ、PR著者のコードを黙って書き換えず、採否はmirugitの議論（ステップ6〜7）で決めるため。

4. **`/review-verdict` で採否を判定する。** 判定なしのアノテーションでは、ユーザーが採否を決められないため。議論中に観点を足すときも同じ定義を使う。

   判定はサブエージェントに `model: opus` を指定して委譲する（軽いモデルは裏取りを省きがち）。委譲前に観点の件数をユーザーに提示し、どこまで委ねるか（多ければアノテーション本文の執筆も）を決めてもらう。

   **裏取りは委譲先の仕事。** 渡すのは指摘の主張と、確かめる場所（対象ファイル・一次資料）まで。「確認済みの事実」として渡すと追認され、こちらの誤りが判定ごと通るため。

   兄弟PRがあるなら、**「対象PRに X が無い」型の指摘には「兄弟PRに X があるか」を確認項目として渡す。** 洗い出し側は対象PRしか見ていないため。1件該当したら同型を全件洗い直す。

5. **対象PRの既存コメント・レビューと照合する。** `gh api repos/{owner}/{repo}/pulls/{number}/comments --paginate` と `.../reviews` で同趣旨の既存指摘を探し、重複はannotateに含めずチャットで除外理由を一言報告する。

   annotate/mirugitを起動せず終えてよいのは、残る指摘も解説対象も無いときだけ。解説対象は大抵見つかるので、終える前にステップ6の兄弟PRの実装との構造的な比較を実際に行ったか確認する。

6. **積み直しの完了を待ってから、`/annotate` でmirugitに反映する。** 積み直したブランチがあれば元の作業ディレクトリで `git checkout <元のブランチ名>-splitted` してから書き出す。アノテーションは指摘系（対応可否を仰ぐ）と解説系（エージェントが解説すべきと判断した箇所）の2種類。配置・順序はレビューしやすさで判断してよいが、1 つの吹き出しに両方を入れない。

   解説系は兄弟PRのレビュー履歴を手がかりにする。兄弟PRで議論済みの概念は不要、出てこなかった新規の概念は対象。兄弟PRや過去PRで結論が出ないまま放置された論点が今回問題として現れていれば経緯ごと取り上げる。

   IMPORTANT: 新規の概念はレビューコメントを読むだけでは見つからない。**兄弟PRの実装と構造的に diff する**（例: 同種リソースの属性の組み合わせを比べ、今回初めて登場するものを grep で特定する）。

   積み直したブランチに付けるときは次を守る。

   - `commit` は**その指摘の行を追加・変更した change**。複数の change にまたがる指摘は最後の change
   - **行番号はその change 時点のファイルから数える**（`jj file show -r <change> <path>`）
   - `--branch` はbookmark名、`--baseCommit` は分岐点（jj-restack-pr Phase 1 の FORK）
   - 書き出す前にreviewセッションを分ける（annotate スキルの「A3. mirugit を起動 + レビューモード開始」にある、別のレビュー対象に移るときの手順）
   - 積み直したブランチを作り直すならアノテーションより前に。`jj squash` / `jj split` は change-id を壊して紐付けが消える

7. **mirugit上の質疑応答に、annotateスキルのフィードバック待ちフローで対応する。**

   - 出すのはユーザーが指示した指摘だけ。レビューコメントか修正PRか分からないときは聞く
   - セッションが`finished`で終わっても指示が無ければ何も出さず、議論をチャットで要約して終える

8. **レビューコメントとして出す**（「ドラフト書いて」「投稿して」）。先に `/review-comment` を Skill 経由で発動する（書き終えてから規約を読むと作り直しになる）。必ずドラフトを経由し、ドラフトの無いまま「投稿して」と言われたら書いて見せてから投稿の指示を待つ。

   **8-1. ドラフトを書く。** 判定が「別 issue」でも、issue の文面ではなく著者に起票を頼むコメントとして書く。

   - 「この観点のドラフトを書いて」は指摘確定の合図。以後採否は蒸し返さず、派生の論点は別の指摘としてドラフトに混ぜない
   - ドラフトはリポジトリ外のファイルに書き、チャットやmirugitの返信には置き場所・投稿先（ファイル:行、対象コミット）・初版からの変更点だけ書く。差し替えのたびに全文が重なると最新が分からなくなるため
   - review-comment は見せる手段に PENDING（GitHub の未提出のレビュー。著者には見えない）を勧めるが、このフローではファイルで見せ、PENDING は 8-3 の投稿でだけ使う
   - アノテーションの本文を流用しない。GitHubコメントは著者が直すのに要る分だけに削る
   - 行番号は元のPR headで取り直す。積み直した change 上の行番号のままだと別の場所に付く

   **8-2. 指示があればドラフトをレビューにかける。** 「ドラフトレビューして」と言われたときだけ、review-comment の「本文の分量」にある別コンテキストのレビューを回し、直したドラフトを見せる。

   **8-3. 投稿の指示でPENDINGとして投稿する。** review-comment の手順に従い、タグ・署名・重複確認を再実装しない。Submit はユーザーがする。

9. **修正PRとして出す**（「PRいれて」「別PRで」「別ブランチで」「ブランチ切って」）。

   **9-1. ブランチを切る。** fork PRなら出し方をユーザーに聞く。そうでなければ元のPR headから仮の名前で、push先が対象PRのブランチにならないよう `--no-track` で切る。

   ```bash
   git switch -c <対象PRのブランチ名>-refactor --no-track origin/<対象PRのブランチ名>
   ```

   大きな機能改善は別ブランチに分ける案をユーザーに示し、採用されたら同じ要領で切ってブランチごとに進める。

   **9-2. コミットする。** メッセージは既存の `git log` に合わせる。

   **9-3. PRにする前に、入れたコミットに合わせてブランチ名を見直す。** 合っていれば仮の名前のままでよい。

   **9-4. baseを対象PRのブランチにして `/create-pr` でPRを作る。**

積み直したなら、フローを終えるときに `jj workspace forget` でワークスペースを片付ける。

## アノテーションの書き方

**観点 → 判定 → 弊害 → 前提 → 対応例** の 5 項目をラベル付きで並べる。現象の描写から入ると「何をしてほしいか」が本文の最後まで出てこないため。

- **観点**: 何をしてほしいかを 1 行で。`[提案]` `[質問]` のように種別を添える
- **判定**: review-verdict の出口ラベルを置き換えて書く（妥当(対応する) → 要対応、妥当(記録する: 議論) → 方針の合意を求める、妥当(記録する: 別課題) → 別 issue、保留 → 判断材料待ち）。他の語や重要度を混ぜない（件間で比べられなくなるため）。却下はアノテーションにせず、チャットで除外理由を一言報告する（ユーザーが覆せるように）
- **弊害**: 直さないと誰がどう困るか。前提より先に来るので、指し先は「下記の」にする
- **前提**: いまどうなっていて、なぜそれが問題か
- **対応例**: 1 つに絞る。案を並べると読み手に選択を投げ返すことになる

裏取りの経緯は本文に書かず、訊かれたら返信で出す（判定が埋もれるため）。他の行・他ファイルへの参照は平文の行番号ではなく annotate スキルの本文アンカー（`mirugit://ref/...` 形式のリンク）にする。

見本（`mirugit://ref/...` は本文アンカーの省略表記）:

````
観点: [提案] 一覧の照合を「シナリオ開始以降」で絞る残課題を、issue に切り出してほしい

判定: 要対応

弊害: 下記の存在チェックは多数のファイル・行で同じ形で使われているのに、注意書きは 1 シナリオにしかありません。他を見る人は気づけず、そのシナリオ固有の問題だと誤解します。

前提: [59 行目](mirugit://ref/...)（ラウンド 1）と [99 行目](mirugit://ref/...)（ラウンド 2）の照合は、[照合の実装](mirugit://ref/...) が 3 キーで行を絞り込んだうえで [同じ 3 キーを検証](mirugit://ref/...) しているため、絞り込みが 1 行でも当たれば必ず通ります。再実行で行が積み上がると、前回が残した行で成立します。

対応例: issue を立てて他のシナリオからも辿れるようにし、[63-68 行](mirugit://ref/...) を 1 行に置き換える。

```
# XXX: 一覧の照合をシナリオ開始以降で絞る残課題は #<issue 番号>
```
````

だめな例（同じ指摘の初版の全文）は [references/bad-example.md](references/bad-example.md)。書く前に一度読み、見本との長さの差を確かめる。

**置き換え・変更を求める指摘は、現在の記述をアンカーと行番号で指し、置換後を実際の文面で書く**（複数行ならコードブロック）。「後半」「以降」のような相対語や「〜にすべき」だけでは範囲と中身が読み手に定まらず、散文の言い換えでは案の穴も出ないため。散らばり自体が指摘の中身なら、現在側も 1 つに集めて並べる。

書き直しの原因は毎回次の 3 つに収まる。書く前に当たらないか確かめる。

- 「この提案」「この指摘」の主語（誰の何か）が無い
- 指摘系と解説系が同じ吹き出しに入っている
- 弊害に挙げた困りごとと違うことに対応例が答えている（読み手が「これで解消されるのか」を自分で補うことになる）

書き直しを頼まれたら、初版の該当文を引用してから直す。本文から消えた記述は引用が無いと追えないため。

**指摘が伝わっていない型のコメント**（「何を言っているか分からない」「単体で分かるようにして」等）**は、返信で補わず親アノテーションの本文を更新する**（annotate スキルの「既存アノテーションの本文を差し替える」）。読み手はスレッドを遡らないため。質問・裏取りの依頼・議論は返信で答える。
