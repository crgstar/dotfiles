# Annotate Review Flow

jj-restack-pr・sentinel・review-verdict・annotate・review-comment はそれぞれ独立したスキル。実行は各スキルに従う。ここでは5つを繋ぐ順序と、繋いだときだけ生まれる判断だけを書く。

## フロー(この順で)

0. **対象PRを `gh pr checkout <番号>` でcheckoutし、差分を用意する。** `gh pr checkout` はローカルに同名ブランチが既にあっても最新のheadへ更新するため、素の `git checkout` のように古いローカル状態のまま進む事故を避けられる。sentinelは既定で `git diff`（ローカルの未コミット差分）を対象にするため、PR番号でのレビューではその前提が成立しない。diffの取り方（base確定・fetch・merge-base diff）は annotate スキルの「モードA → A2. 対象の決定」と同じ手順に従い、これをsentinelに渡す対象として明示する（GitHubの「Files changed」と同じ基準にするため）。

1. **兄弟PR（同じbaseから並行分岐した未マージPR等）の有無をユーザーに確認する。** 決めつけない（ある場合とない場合の両方が普通にある）。ある場合は、その兄弟PRの差分に加えて既存のレビューコメント・議論も取得する。差分はsentinelに渡して比較対象として実際に評価させる（設計方針の矛盾・同一ロジックの重複実装等を検出するため。存在を記録するだけでは比較にならない）。レビュー履歴はステップ6で解説系の判断材料に使う。兄弟PRが複数・レビュー履歴が長い場合、取得作業はサブエージェントに委譲してよい（メインコンテキストを埋めないため）。

   **比較は両方向に使う。** 兄弟PRの差分は指摘を作る根拠にも、退ける根拠にもなる。検出のためだけに渡すと、退ける材料が判定側に届かない。

2. **jj-restack-pr をサブエージェントに委譲し、PR差分を review 単位の change に積み直させる。** ステップ5までと並行して走らせる。積み直しは差分の中身を変えないので、sentinelに渡す対象は変わらない。

   **作業場所は `jj workspace add` で切った別ワークスペース**（リポジトリ外の一時ディレクトリ）。積み上げの途中は作業ツリーが層ごとの中間状態になるため、同じディレクトリだとsentinelと判定の委譲先が欠けたファイルを読む。別ワークスペースなら本体の作業ツリーとgit HEADは動かず、commitは同じオブジェクトストアに入るので本体から取り出せる。

   実行は jj-restack-pr に従う。この流れ固有の差分は次の3点。

   - モードは読み順。ユーザーが「最小構成で」と言ったときだけ最小構成にする
   - **Phase 7 の `git checkout` はやらせない。** 本体のgit HEADはステップ0のPR checkoutのまま保つ。bookmarkを付けたら `jj git export` まで進ませる（exportしないとbookmarkがgit側に出ず、本体から列を見られない）
   - 完了報告は層ごとに change-id・commit id（gitのコミットハッシュと同じもの）・タイトル・対象path。ステップ6でアノテーションの付け先に使う

   **委譲先に承認を求めさせない。** ステップ3〜5と並行させる意味が無くなるため、jj-restack-pr が立ち止まる分岐は次の既定で自分で決めさせ、決めた内容を完了報告に書かせる。

   - Phase 2 のプランは承認を取らずそのまま Phase 3 へ進む。Phase 4 の検証が落ちてプランを直したときの再承認も取らない。層の並びと対象pathは完了報告で受け取る
   - jj repo でなければ本体を colocate 化して進む（`.jj` が増えるだけで作業ツリーのファイルは変わらず、`rm -rf .jj` で戻せる）
   - hunk が混在するファイルは三択の (a)（最終状態から中間状態を手で作って積む）
   - 検証コマンドはリポジトリの規約から探し、見つからなければ層ごとの検証を飛ばす（積み直し前後の内容一致の検証は飛ばさない）
   - bookmark を付ける前の連絡待ちもしない。列を読むのはステップ6以降のこの流れ自身なので、待つ相手がいない

   積み直しが成立しない場合（層が1つ・fork PR・最小構成で元の履歴が既に各コミット単位で通る等）と途中で失敗した場合は、待たずにそのまま進める。ステップ6は元のPR headに対するアノテーションになる。

3. **sentinelで指摘を洗い出す。** sentinelの自動即決フェーズは使わず、集約した指摘はそのまま次のreview-verdictに渡す。ここで即決させると、mirugitで議論する材料が失われる。

   IMPORTANT: **sentinelのフェーズ3.5「先行修正」は使わない。** 対象は他者（PR著者）が既に提出したコードであり、レビュアーが黙って書き換えてよい対象ではないため、指摘の性質を問わずfix/skip判断はユーザーに委ねる。

   IMPORTANT: **sentinelのフェーズ4（auq-webでのfix/skip確認）も使わない。** mirugit上のアノテーション議論（ステップ6〜7）が同じ役割を担うため、auq-webを挟むと意思決定が二重・別チャネルになりユーザーを混乱させる。

   IMPORTANT: **sentinelのフェーズ3（一次情報・兄弟ファイルとの突き合わせ）もこちらでは行わない。** 裏取りはステップ4の委譲先に寄せる。担当が2箇所に分かれると同じ確認を二重にやることになり、メインコンテキストも埋まる。

4. **`/review-verdict` で採否を判定する。** sentinelの集約結果をそのままannotateに流さない。判定なしのアノテーションは「調べた結果」だけが並び、ユーザーが採否を決められないため。review-verdict の実害段・分類の定義は、mirugitでの議論中に観点を足すときも同じものを使い回す（定義がぶれると件間で比較できない）。

   判定はサブエージェントに委譲する。委譲の前に観点の件数をユーザーに提示する。件数によってどこまで委ねるかが変わり（多ければステップ6のアノテーション本文の執筆も同じエージェントに任せてよい）、それを決めるのはユーザーだから。

   **裏取りは委譲先の仕事。** こちらで先に確かめて「確認済みの事実」として渡さない。渡すのは指摘の主張と、どこを見れば確かめられるか（対象ファイル・一次資料の在り処）まで。確認済みとして渡すと追認されやすく、こちらの誤りが判定ごと通ってしまうため。

   兄弟PRがあるなら、**「対象PRに X が無い」型の指摘には「兄弟PRに X があるか」を指摘ごとの確認項目として渡す。** 洗い出し側は対象PRの作業ツリーしか見ておらず、構造上この確認ができないため。判定済み・議論中を問わず、1件該当したら同型を全件洗い直す。

5. **対象PRの既存コメント・レビューを確認する。** `gh api repos/{owner}/{repo}/pulls/{number}/comments --paginate` と `.../reviews` で、人間レビュアーやCopilot等が既に同趣旨の指摘をしていないか見る。重複していればその指摘はannotateに含めない（チャットで一言、除外理由を報告する）。sentinelの指摘内容が確定するまで一致判定はできないため、この順（洗い出し→照合）で行う。

   ```
   remaining_findings = sentinelの指摘の集合 - 既存コメントと重複する指摘
   ```

   annotate/mirugitを起動せず終了してよいのは、`remaining_findings` が空集合で、かつ解説対象も無い場合だけ。どちらも無いことは稀（解説対象は大抵1件は見つかる）なので、終了を選ぶ前にステップ6の構造diffを実際に行ったか確認する。

6. **積み直しの完了を待って合流し、`/annotate` でmirugitに反映する。** 積み直した列があるなら、本体で `git checkout <元のブランチ名>-splitted` して列を出してから書き出す（無いときは元のPR headのまま書き出す）。アノテーションは指摘系（`remaining_findings` の各要素。対応可否の判断を仰ぐもの）と解説系（対応可否を問わない。差分を見てエージェントが「解説しておいた方が良い」と判断した箇所に付ける）の2種類。両者を別のファイル・行に分けるか、同じファイル・行に別々の吹き出しとして並べるかは固定しない（1 つの吹き出しに両方を入れないことだけ守る）。ユーザーが最もレビューしやすい順序・粒度になるようエージェントが判断する。

   解説系を付けるかどうかは、兄弟PRのレビュー履歴（ステップ1で取得）を手がかりにする。兄弟PRで既に議論・レビュー済みの概念は、今回のPRでも解説不要（重複するため）。逆に兄弟PRの議論に出てこなかった新規の概念は解説対象になりやすい。また、兄弟PRや過去PRで宙吊りのまま終わった論点が今回のPRで問題として現れている場合は、その経緯も含めて取り上げる。

   IMPORTANT: 「新規の概念」はレビューコメントを読むだけでは見つからない。レビュアーがたまたま言及しなかっただけの新規パターンを見逃すため、**兄弟PRの実装（コード自体）と構造的に diff する**（例: 同種リソースの属性の組み合わせを兄弟間で比較し、今回のPRで初めて登場する組み合わせを grep 等で特定する）。

   積み直した列に付けるときは次を守る。

   - `commit` は**その指摘の行を入れた層**のcommit。複数の層にまたがる指摘は最後の層に付ける
   - **行番号はその層のファイルから数える**（`jj file show -r <change> <path>`）。最終状態の行番号は途中の層とずれる
   - `--branch` はbookmark名、`--baseCommit` は分岐点（jj-restack-pr Phase 1 の FORK）
   - レビュー対象が変わるので、書き出す前にreviewセッションを分ける（annotate スキルの A3）
   - 列を作り直すならアノテーションより前に。`jj squash` / `jj split` は change-id を壊して紐付けが消える（describe・rebase・並べ替えは残る）

7. **mirugit上での質疑応答に、annotateスキルのフィードバック待ちフローに従って対応する。** ここでの応答内容が、次の投稿判断（ステップ8でどの指摘を選ぶか）の材料になる。

8. **ユーザーが明示的に指定した指摘だけを `/review-comment` で投稿する。** 議論した指摘を自動で全部PRに上げない。「これを投稿して」と言われたものだけを対象にする。mirugitセッションが`finished`で終わっても、投稿依頼が無ければ何もPRに投稿せず、議論内容をチャットで要約して終える。

   **行番号は元のPR headで取り直す。** 投稿先は元のPRなので、層の行番号のままだと別の場所に付く。積み直したなら、終わったあとワークスペースを `jj workspace forget` して片付ける。

## アノテーションの書き方

**観点 → 判定 → 弊害 → 前提 → 対応例** の 5 項目をラベル付きで並べる。現象の描写から入ると「何をしてほしいか」が本文の最後まで出てこないため。

- **観点**: 何をしてほしいかを 1 行で。`[提案]` `[質問]` のように種別を添える
- **判定**: 採否の結論を短く（要対応 / 方針の合意を求める 等）
- **弊害**: 直さないと誰がどう困るか。前提より先に来るので、指し先は「下記の」にする
- **前提**: いまどうなっていて、なぜそれが問題か
- **対応例**: 1 つに絞る。案を並べると読み手に選択を投げ返すことになる

裏取りの経緯は本文に書かない。訊かれたら返信で出す。本文が伸びるほど判定が埋もれるため。

他の行・他ファイルへの参照は平文の行番号ではなく annotate スキルの本文アンカーにする。平文だと読み手が手で探すことになり、相互参照が死ぬため。

見本（`mirugit://ref/...` は本文アンカーの省略表記）:

````
観点: [提案] 一覧の照合を「シナリオ開始以降」で絞る残課題を、issue に切り出してほしい

判定: 要対応

弊害: 下記の存在チェックは多数のファイル・行で同じ形で使われているのに、注意書きは 1 シナリオにしかありません。他を見る人は気づけず、そのシナリオ固有の問題だと誤解します。

前提: [59 行目](mirugit://ref/...)（ラウンド 1）と [99 行目](mirugit://ref/...)（ラウンド 2）の照合は、[照合の実装](mirugit://ref/...) が 3 キーで行を絞り込んだうえで [同じ 3 キーを検証](mirugit://ref/...) しているため、絞り込みが 1 行でも当たれば必ず通ります。再実行で行が積み上がると、前回が残した行で成立します。

対応例: issue を立てて他のシナリオからも辿れるようにし、[63-68 行](mirugit://ref/...) を 1 行に置き換える。

```
# XXX: 一覧の照合をシナリオ開始以降で絞る残課題は #<issue 番号>
```
````

だめな例（同じ指摘の初版。全文。上とどれだけ違うかを見るため省略していない）:

```
一覧の照合を「シナリオ開始以降」で絞る残課題を、spec 内の XXX コメントではなく issue に切り出してほしい、という提案です。この PR でコードを直すことは求めていません。

判定: 記録先を揃えることを求める（コード変更なし。issue 起票と XXX の置き換えのみ）

前提: 59 行目と 99 行目の「詳細画面の一覧に <file> と同じ内容の行が表示される」は、実装（`<照合の実装>:44-84`）が分類名・変更前の値・変更後の値の 3 キーで行を絞り込んだうえで、**その同じ 3 キーを検証しています**。絞り込みが既にその 3 値で一致した行を選んでいるので、検証部分は必ず通ります。実質は「その 3 値を持つ行が 1 行でもあるか」の存在確認で、件数でも時刻でも絞っていません。環境を作り直さずにローカルで回すと行は積み上がるので、2 回目以降は前回実行が残した行でこの照合が成立します。

60〜68 行の XXX にこの残課題が書かれていて、「本筋は一覧側にも『シナリオ開始以降』の絞り込みを入れること」で終わっています。一方この PR の最後のコミットは「未検証のまま残る観点は issue として起票したので、コード側にコメントは残さない」という方針を明示しています。**この残課題だけ、その方針から外れて spec の中に残っています。**

確かめたこと: 照合の実装（絞り込みを 3 回重ねて先頭の行を取り、その行の同じ 3 キーを検証している）。起票済みの issue のタイトルを全部開いて、一覧の照合を扱うものが無いこと。影響範囲については 2 点補足します。

- 1 回の実行の中では恒真になりません。ラウンド 1 とラウンド 2 の期待値ファイルは分類名が違うので、ラウンド 1 が残した行でラウンド 2 が通ることはありません。恒真になるのは環境を作り直さずに回した 2 回目以降だけで、CI では踏みません
- 変更前の値そのものが無検証というわけではありません。別ディレクトリのケースが、詳細画面の値を恒真ではない実比較で照合しています

対応例: 「一覧の照合をシナリオ開始以降の件数で見る」issue を立て、60-68 行の XXX のうち後半（「一方、直前の一覧の照合は…本筋は一覧側にも『シナリオ開始以降』の絞り込みを入れること。」）を、その issue 番号への参照 1 行に置き換える。前半（別の履歴を件数で見る理由）はこの PR で実装済みなので残す。
```

**置き換え・変更を求める指摘は、現在の記述をアンカーで指し、置換後を文面で示す。** 「〜に置き換えないこと」「〜にすべき」だけでは、何を何にする話かが読み手に定まらないため。置換する範囲は「後半」「以降」のような相対語でなく行番号で示す。相対語だと著者が範囲を自分で決めることになる。散らばり自体が指摘の中身なら、現在側も 1 つに集めて並べる。

置換後は実際の文面を書く（複数行になるならコードブロックで）。散文で言い換えている間は通っていた案の穴が、書き下すと出るため。

書き直しの原因は毎回同じ 3 つに収まる。書く前に自分の文がこれに当たらないか確かめる。

- 「この提案」「この指摘」の主語（誰の何か）が無い
- 指摘系と解説系（対応可否を問うものと問わないもの）が同じ吹き出しに入っている
- 弊害に挙げた困りごとと違うことに対応例が答えている（読み手が「これで解消されるのか」を自分で補うことになる）

書き直しを頼まれたら、初版の該当文を引用してから直す。本文から消えた記述は引用が無いと追えないため。

**反映先は、コメントが何を指しているかで決める。** 指摘が伝わっていない型（「何を言っているか分からない」「前提の説明が不足」「単体で分かるようにして」）は、返信で補わず親アノテーションの本文を更新する（手順は annotate スキルの「既存アノテーションの本文を差し替える」）。読み手はスレッドを遡って読み直さないため。質問・裏取りの依頼・議論は返信で答える。

## ドラフトと投稿

ドラフトはチャットではなくファイルに書く（リポジトリに入らない場所）。差し替えを繰り返すため、チャットだと最新版がどれか分からなくなる。**mirugit の返信にも全文を貼らない。返信に書くのはドラフトの置き場所・投稿先（ファイル:行、対象コミット）・初版から変えた点だけにする。**同じ文面が複数の場所にあると、差し替えたときにどれが最新か分からなくなるのは同じため。

**「この観点のドラフトを書いて」と言われたら、その観点は指摘として確定した合図**。以後その観点の採否は蒸し返さず、文面と投稿だけを扱う。確定後の議論で出た派生の論点も、別の指摘として扱いドラフトに混ぜない。ユーザーが承認したものと別物になるため。

投稿は `/review-comment` を Skill 経由で発動して行う。タグ・署名・PENDING 既定・重複確認をこのフロー側で再実装しない。

本文の分量も review-comment に従う。アノテーションとGitHubコメントは読み手が違い、前者はユーザーが採否を判断するための根拠を残す、後者は著者が直すのに要る分だけに削る。
