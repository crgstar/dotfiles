# Comment Scrutiny

## 判定の軸

**残すのは「消すと壊れる」コメントだけ** — 消したとき将来の編集者が壊す方向に動くもの。それ以外（コードや型から読める情報、定石レベルの why、別システムへの言及、同じ why の言い直し）は削除する。残す場合も why の核 1〜2 文に収める。超えるなら機構の解説を積んでいる。

コードに現れる具体語（画面表示の文字列・列名）は、コメントと重複していても残す。抽象表現に置き換えると、コメントがコードのどこを指すのか辿れなくなるため。

テストコードの fixture・テストデータ選択の意図コメントは、「消すと壊れる」と正当化できても削除に倒す — 意図は値の形・テスト名・assert で表現できるため。

## 書き直すときの原則

**支配している条件（発火条件・制約・不変条件）から書き出し、それに照らした帰結を後に置く。** 裏取りした順（前提データ → 推論 → 結論）で書くと、読み手は最後まで読まないと何の話か分からない。

**その位置から確かめられない語を書かない。** 別ファイルの引数名・設定キーや、前の文へ遡らないと指すものが分からない言い方（「同じ状態」）は、読み手が辿れずコメントごと信用されなくなる。

**提案文の名詞・動詞を 1 語ずつ、「何の」「何が・何を・どこへ」で問う。補えないなら、その語を使わずに書き直す。** 補えない語は、別の場所を見に行っても指す対象が定まらない。入力に書かれていた語も例外にしない。
例: 「フラグを立てる」→ 何のフラグか・立てると何が変わるかが補えない →「再送済みフラグを true にし、次の巡回で送らない」

**関数の doc はその関数の契約（何をどこまでするか）で閉じ、契約から外れたときの対処は呼び出し側へ持ち越す。** 契約の外を書くと、doc がその関数の説明ではなくなる。

## 手順

1. 差分（未指定なら未コミット差分）の追加・変更行からコメントを含む行を抽出
2. 各コメントの周辺コードを読み、「消すと壊れる」かを判定して分類
3. 短縮・残すと判定したコメントの提案文を「書き直すときの原則」に 1 本ずつ当て、`unslop` に通す
4. 結果を表形式で報告

## 出力形式

| 対象 | 処理 | 判断理由 |
|---|---|---|
| `file.ts` L42 コメント内容 | 削除 | コードの言い換え。`x ?? default` から読める |
| `file.ts` L58 コメント内容 | 短縮 → `提案文` | 消すと壊れるが挙動説明が冗長 |
| `file.ts` L73 コメント内容 | 残す | spread で narrow 崩れ回避。消すと flat 化される |
