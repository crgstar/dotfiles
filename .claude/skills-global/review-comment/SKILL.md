# Review Comment

## 投稿前にやること(この順で)

1. **重複確認**: `gh api repos/{owner}/{repo}/pulls/{number}/comments --paginate` を `created_at` 順に並べ、同じ指摘が既出(対応済み/未対応問わず)なら投稿しない。他のレビュアーが既に広範にレビュー済みの PR では特に重複しやすい。
2. **一次情報での裏取り**: 「〜のはず」で終わらせず、再現コード・grep・API仕様等で実際に確認してから文面にする。裏取りしていない主張は後で崩れる。
3. **ドラフトを見せて確認を取る**: 本文は「本文の分量」に従い、ユーザーに見せる前に同節のレビューを挟む。PRコメントは他人に見える公開行為なので、投稿先(ファイル:行、対象コミット)と本文を提示し、ユーザーの了承が出るまで公開しない。**見せる手段は PENDING が最良**で、diff 上の実物と suggestion の適用可否まで確認できる(下記「PENDING(下書き)で投稿(既定)」)。ドラフトが溜まったまま提示を先延ばしにしない。
4. **`unslop` が当たっていることを確かめる**: 太字の飾り・矢印での代用・中身のない述部が残ると、直してほしいことが埋もれる。
5. **重要度タグ**: このスキル経由で投稿するコメントには必ず `[must]`/`[should]`/`[may]` を付ける(対象PRにその慣習が無くても付ける)。どのタグが適切か迷う場合はユーザーに確認する。
6. **署名**: 特に指示が無ければ `🤖 Generated with [Claude Code](https://claude.com/claude-code)` を付ける(`create-pr` と同じ慣習)。
7. **置き換えを頼む指摘は suggestion にする**: 下記同名の節に従う。
8. **投稿方式は PENDING が既定**: ユーザーが即時公開を明示していない限り、下記「PENDING(下書き)で投稿(既定)」の手順を使う。投稿前に対象PRで自分(gh認証ユーザー)のPENDINGレビューが既に開いていないか確認しておくと、後段の分岐がスムーズ。

## 本文の分量

残すのは **読み手が自力ではすぐ辿り着けない事実だけ**。長い本文は読み流され、直してほしいことが埋もれるため。

文ごとに「この文が無かったら著者は何が分からなくなるか」を問う。アンカーの行を開けば見える・著者が自分で書いた・grep 1 回で出る・suggestion が示している・考えれば分かる、のどれかなら落とす。ただし弊害(直さないと何が起きるか)はこの判定にかけない。落として残るのは、調べて初めて分かったこと(別リポジトリ、CI ログ、git 履歴、横断集計、動かさないと出ない結果)になる。1 行の文言・宣言・テスト名を直す類が 1〜2 文で終わっていないなら、判定を通っていない文が混ざっている。

弊害は必須ではないが、書くなら 1 文。

**字数や行数を目標にしない。** 必要な長さは観点の複雑さで決まる。満たしやすい代理指標があると、そちらで合格と判断して本来の基準を詰めなくなるため。

**問題ない箇所には触れない。**「ここはこのままで正しいと思います」は指摘ではない。書くと読み手が直す対象を本文から探すことになるため。

出典は主張の真偽確認に不可欠なもの 1 つに絞る。

1 コメント 1 関心事。短縮で別の修正依頼が落ちるなら、削らず別コメントに分離する。2 つ入れると前半だけ直されるため。

短縮・推敲(`unslop`)・ドラフトのレビューは別コンテキスト(サブエージェント)に一続きで任せ、この節の基準を渡す。工程を分けると、推敲側は分量を動かせず長さが固定される。引用(ファイル:行、対象コミット)と現物の照合も同じエージェントにやらせる。読み手にとって既知の事実が混ざっていることも、関心事が同居していることも、引用のずれも、自分が書いた文では見えないため。

サブエージェントの指摘は、本文に入れる前に自分で導き直す。根拠まで確かめずに取り込むと、誤りをこちらの主張として公開することになる。

## 本文の語彙

読み手は著者で、こちらの下書きも調査過程も見ていない。次の 3 つを本文に持ち込まない。

- **自分が作った略語・比喩**。使うなら初出で実体を書く。定義せずに繰り返すと、読み手は最後まで意味を推測し続ける
- **リポジトリ内部でだけ通じる語**。設定ファイルや慣習の中の語は、指しているものを直接書く
- **下書きの符号**(案 A / 案 B、通し番号)。ユーザーとの会話でも使わない。指すものは「どのファイルの何行の、何をする指摘」で言う

## 投稿先コミットの取り違えに注意

`git log --oneline main..origin/main` 等でローカルブランチが origin より古くないか確認してから対象行番号を数える。古いローカルの行番号で `commit_id` に最新 SHA を指定すると、行がズレて別の場所にコメントが付くか API エラーになる。

`commit_id` は `gh pr view {number} --json headRefOid --jq .headRefOid` で取れる PR の現在の head SHA を使う(fork からの PR でも同様に head SHA でよい)。

下書きを書いてから投稿するまでに著者が push して head が変わることがある。**投稿直前にもう一度 head SHA を取り、下書き作成時と違っていたらアンカーを取り直す。** 既に直った指摘が混ざっていないかもそこで見て、直っていれば投稿しない。

**アンカーを取り直したら本文中の行番号参照も取り直す。** 投稿先の行だけ直しても本文の「NN 行の〜」は古いまま残り、読み手は別の場所を見にいく。

範囲を指すコメントは `startLine`/`startSide` を添えて複数行コメントにする。アンカーは diff の新側に存在する行だけを指定する。無い行を指定すると API エラーか別位置に付くため。

## 置き換えを頼む指摘は suggestion にする

現在と置換後を本文に並べる代わりに、コードフェンスの言語指定に `suggestion` を書いたブロックで出す。差分の形で読めるうえ、著者が 1 クリックで適用できるため。

**一から書き起こすコードは載せない。** 新規のテストや関数そのものは、雛形になる既存箇所を 1 つ示して終える。実装は著者が決めること。

アンカー行範囲が**まるごとブロックの中身に置き換わる**。差分ではなく置換後の全文を入れ、範囲を置換対象と正確に一致させる(`startLine`/`startSide` 付きの複数行コメント)。1 行だけ指したコメントに複数行のブロックを入れると、その 1 行が全文に差し替わって前後が壊れる。

**「1 つに収まらない」と判断する前に試す。** 変更の形を変える(呼び出し側でローカル変数に持つ等)、間の未変更行を含めてアンカーを広げる。一度諦めると以降その判断を疑わないため。

**コメントは現在のソースに対して書く。** 別のコメントの suggestion を適用した後の状態を前提にしたコメントは書かない。単独で適用すると壊れ、適用順にも依存するため。

ファイルをまたぐ置換は 1 つの suggestion に入らない。ファイルごとに別コメントにし、理由は片方に書いてもう片方から参照する(同じ理由を 2 度読ませないため)。1 つ目に畳んで残りを文章で添えると、suggestion は 1 クリックで適用できるので、そこで作業完了と見なされて文章側が落ちる。

**そのまま適用しても動かない案でも suggestion で出す。** 1 クリックで適用できることより、差分の形で読めることの方が価値がある。「これだけでは動かないが、こういう形」を示す用途に使ってよい。付随する変更(別ファイル、新規ファイル、呼び出し側の書き換え)を本文に書き添え、単独では通らないことを suggestion の直後に書く。

**足りないものを正確に書くために、適用状態で検証コマンドを最後まで通す。** 型チェックだけで済ませない — テストダブルが型キャストされていると、メソッド追加の必要性は型チェックを通り抜け、テスト実行で初めて落ちる。何が足りないか分からないまま「動かないかもしれません」と添えるのは、著者に調査を投げているのと同じ。

投稿後にアンカーの行範囲は変えられない(下記「PENDING コメントの書き直し」は body だけ)。`deletePullRequestReviewComment`(PENDING でも消せる) で消してから作り直す。

## PENDING(下書き)で投稿(既定)

ユーザーが即時公開を明示していない限り、これが既定の投稿方式。GitHub は**1ユーザー・1PRにつき PENDING レビューを1つまで**しか許さないため、まず既存の有無を確認してから分岐する。

**中身は必ずインラインコメントに入れる。レビュー本文(review の `body`)には置かない。** API で設定した body は「Finish your review」欄には出ないので、読み手に届かない。PR 全体にかかる話も、代表する 1 行にアンカーして書く。

**なぜ既定がPENDINGか**: 一度 `pulls/.../comments`(通常投稿)で即時公開すると、後から「PENDINGにして」と言われた場合に「PENDINGへ同内容を追記→公開済みの元コメントを削除」という往復が発生する(下記「公開済みをPENDINGに変換」参照)。投稿前にPENDINGを選んでおけばこの手戻りが要らない。

**まだ PENDING レビューが無い場合**は `event` を省略して作る(`event` を渡すと即座に公開されてしまう):
```bash
gh api repos/{owner}/{repo}/pulls/{number}/reviews \
  -f commit_id="<head SHA>" \
  -F 'comments[][path]=path/to/file.go' -F 'comments[][line]=123' \
  -F 'comments[][side]=RIGHT' -F 'comments[][body]=...'
```

**既に PENDING レビューがある場合**、それに追記するには GraphQL の `addPullRequestReviewThread` を使う(`line`/`side` を直接指定できる。似た名前の `addPullRequestReviewComment` は旧い diff `position` 指定が必要で使いにくいので避ける)。

1. 対象レビューの node id を取得する(PENDING は authorから見た自分のものしか出てこない):
   ```bash
   gh api graphql -f query='{ repository(owner:"O", name:"R") { pullRequest(number: N) {
     id
     reviews(first: 20) { nodes { id databaseId state author { login } } }
   } } }'
   ```
2. 見つけた `pullRequestReviewId` へ追記する:
   ```bash
   gh api graphql -f query='
   mutation($reviewId: ID!, $body: String!, $path: String!, $line: Int!, $prId: ID!) {
     addPullRequestReviewThread(input: {
       pullRequestId: $prId, pullRequestReviewId: $reviewId,
       body: $body, path: $path, line: $line, side: RIGHT
     }) { thread { comments(first: 1) { nodes { databaseId } } } }
   }' -f prId="<PR node id>" -f reviewId="<review node id>" \
      -f body="$(cat draft.txt)" -f path="path/to/file.go" -F line=123
   ```

既存の PENDING レビューには**ユーザー自身が書いたコメントが入っていることがある**。追記前に中身を確認し、Submit するとユーザーの分も同時に公開されることを伝えて公開判断を委ねる。

## PENDING コメントの書き直し

PENDING のコメントは REST の `pulls/comments/{id}` から見えない(404)。投稿後に文面を直すときは GraphQL の `updatePullRequestReviewComment` を使う。node id は上のレビュー取得クエリに `comments(first: N) { nodes { id path line } }` を足し、path + line で対応付ける。

ドラフトをファイルに置いた場合は、書き直しをファイル側にも反映する。二重管理になると次の差し替えで GitHub と食い違うため。

## 即時公開したいとき(ユーザーが明示した場合のみ)

`gh api repos/{owner}/{repo}/pulls/{number}/comments` に `body`/`commit_id`/`path`/`line`/`side` を渡す。1回の呼び出しごとに GitHub が自動でその1件だけを含む単発レビューを作り、即座に `COMMENTED`(公開)状態になる。

## リカバリ: 公開済みのコメントを PENDING に変換したい場合

これは正規の投稿順ではなく、**誤って(または指示を確認する前に)即時公開してしまった後のリカバリ手順**。投稿前にPENDING希望と分かっているなら、上の「PENDING(下書き)で投稿(既定)」を最初から使うこと。

投稿後に「これ下書きにして」と言われた等の場合:
1. 上記の手順で PENDING レビューに同内容を追記する
2. 公開済みの元コメントを削除する: `gh api -X DELETE repos/{owner}/{repo}/pulls/comments/{id}`

削除を先にやると本文を失うので、必ず「追記してから削除」の順で行う。
