## 基本原則

初見の Claude Code の判断・行動を変えない行は削る。
長く正確に書くよりも、短く印象に残る書き方をする。多少抽象的でも、長文は読み流されて行動を変えないため。

ルール・表・チェックリストを書きたくなったら一旦止めて、スタンス 1 文にできないか試す。
迷ったら短い方を選ぶ。
ただし実行順序そのものが判断材料になる逐次手順は、スタンス化せず短い番号リストのまま残す。

ただし「印象に残る」 を警句や煽り文句で達成しない。抽象ルールには why を 1 文添える。
why は判断を変える根拠 1 文に限る。経緯・代替案・トレードオフは実行に不要なので書かない（git log / memory へ）。
改修でも同じ。追加分だけ別系列の番号にする・廃止分を取り消し線で残す・承認日付や到達過程を書くといった差分の痕跡は残さず、最初からそう書かれていた形に直す。読み手に要るのは最終状態だけのため。

依存スキル・CLI の仕様は写経しない。「実行は X に従う」と書き、自分側固有の差分だけ残す。
依存先が更新されたとき drift するため。連携を書く前に依存先を動かして挙動を確かめる。
写経とはフラグ・仕様の網羅列挙のこと。繰り返しハマる要点は「複数構文があり混同しやすい」程度の 1 行で残し、詳細は依存先へ誘導する。

環境固有の識別子（メールアドレス・絶対パス・組織名等）は SKILL.md に含めない。public リポに入ると取り消せないため。

## コードブロック

停止すべき条件（取得失敗・dirty・0 件等）は散文の注意書きでなく、exit するガードとしてコードに置く。散文は実行者に素通りされるため。
Bash 呼び出し間でシェル変数は消える。複数ブロックに跨る値は持ち越さず、各ブロック冒頭で再導出する。

## description

対象物 + 発動条件 + 除外条件 を揃える。動詞中心ではなく対象物で語ると誤発動が減る。
圧縮の原則は本文向け。発動可否は description の語マッチで決まるため、トリガー語の列挙は削らない。
本文の手順要約を書かない。要約があると、本文を読まずに description だけで実行されるため。

## 書いたら subagent でレビュー

収束を確認してから完了と報告する。

新規作成・大改修ではまず `general-purpose` subagent へ
「この SKILL.md に従って<サンプルタスク>を実行し、書かれておらず自分で埋めた前提を、その値ごと列挙せよ」と依頼し、
申告を吟味してから下記の reviewer レビューへ進む。
書き手には自明でも初見のモデルには曖昧な境界を、実測で洗い出すため。
サンプルタスクには境界状態（0 件・空入力・base が main でない等）を混ぜる。正常系だけでは場合分けの欠落が表に出ないため。
同じサンプルタスクは最低 2 体に並列で回す。1 体では「たまたまその値を埋めた」と「放っておいても着く」を区別できないため。

申告された前提は、値が回した全ての体で書き手の意図どおりなら書かず（規定が無くても着いた証拠）、
値が意図と食い違うか、体ごとに割れて手順の実行が壊れるものだけ書く。

節構成・Phase 番号・スキル名を変えたら、旧ラベルへの参照を配下スクリプト含め grep する。取り残しは reviewer の目視より grep が確実なため。検索語は 1 パターンで終わらせず、同じ概念の別呼称と、番号を伴わず次の手順・スキルを名指しする参照も含める。

`skill-md-reviewer` サブエージェント（`subagent_type: skill-md-reviewer`）に、レビュー対象 SKILL.md、
この SKILL.md のフルパス、反復ラウンド（1 回目か 2 回目以降か。2 回目以降は前回の指摘とその対応）を
渡してレビューを依頼する（基準は本ガイドを Read させる。写経しない）。
レビュー対象は今回変更した箇所に限る。pre-existing 行への指摘はスコープ外として却下する。
妥当な指摘だけ反映し、却下する指摘は理由を次ラウンドで reviewer に渡す。
再レビューは最大 3 回。新規指摘が 0 件なら収束で、上限到達は収束ではない。3 周で 0 件にならなければ、最終ラウンドで直した箇所も未検証で残るので、却下した残件と併せてリストでユーザに渡す。
