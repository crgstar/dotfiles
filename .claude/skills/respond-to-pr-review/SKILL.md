# PR Review Response Workflow

## Phase 0: 対象ブランチのチェックアウト

現在の作業ツリーが PR のブランチでない場合、修正を適用できる状態を先に作る。

1. 判定材料を取得する:
   ```bash
   git branch --show-current
   gh pr view {number} --json headRefName,author --jq '{head: .headRefName, author: .author.login}'
   git status --porcelain  # 出力があれば dirty
   ```
2. 現在のブランチが PR の head ブランチならそのまま進む。それ以外（別ブランチ・dirty・他人の PR）は、作業ツリーを切り替えず **worktree** でチェックアウトする。配置は `git worktree list` で既存の PR 用 worktree の前例を確認して踏襲する。
3. `fatal: '<branch>' is already used by worktree` が出たら `git worktree list` で状態を確認し、`prunable` な worktree なら `git worktree prune` してから追加する。生きている worktree ならそちらで作業する。

## Phase 1: PR検出とコメント取得

1. PR番号を特定する。引数があればそれを使い、なければ現在のブランチから自動検出する:
   ```bash
   gh pr view --json number --jq '.number'
   ```
2. レビュー指摘を **3 ソースすべて**から取得する（インラインだけでは diff 外の指摘を取りこぼす）:
   ```bash
   # (a) インラインコメント（in_reply_to が付くものは既存スレッドへの返信）
   gh api repos/{owner}/{repo}/pulls/{number}/comments --paginate \
     | jq '[.[] | {id: .id, path: .path, line: .line, body: .body, user: .user.login, in_reply_to: .in_reply_to_id}]'
   # (b) issue コメント（diff 外の指摘はここに来る）
   gh api repos/{owner}/{repo}/issues/{number}/comments --paginate \
     | jq '[.[] | {id: .id, body: .body, user: .user.login}]'
   # (c) レビュー本文（Approve/Comment 時のまとめ文。body が空でないもの）
   gh api repos/{owner}/{repo}/pulls/{number}/reviews --paginate \
     | jq '[.[] | select(.body != "") | {id: .id, state: .state, body: .body, user: .user.login}]'
   ```
3. 既対応の除外: `in_reply_to` で束ねたスレッドの末尾が自分側（PR 作者側）の返信なら対応済みとして除外する。issue コメントも自分側の返信・報告は除外する。
4. 残った未対応コメントをユーザーに一覧表示する（指摘者、ファイル、内容、ソース種別）。

## Phase 2: コード修正

各コメントに対して:

1. 該当ファイルを Read で読み、指摘内容を理解する。
2. AIレビュアー（Copilot等）の指摘は前提を検証してから対応する。型エラーの指摘なら `tsc --noEmit` で実際にエラーが出るか確認する。前提が誤りなら対応不要としてユーザーに報告する。
3. **過去 PR での既決着チェック:** 同ファイル・同ドメイン・兄弟コンポーネントに対する過去 PR のレビュー履歴を確認する。同じ指摘（特に AI レビュアーによる類型的指摘）に既に判断が下されていれば、その判断を尊重して同じ根拠で回答する。兄弟ファイルで「対応不要」と決着済みの指摘に対して今回だけ対応すると、対称性が崩れる。慣習の有無はリポ横断で反例（未対応箇所）も数えて判定する（肯定例の拾い読みは「整備済み」の誤回答を生む）。レビュー履歴の確認コマンド例: `gh pr list --search "<関連キーワード>" --state merged` → `gh api repos/.../pulls/<番号>/comments`。
4. 2（前提検証）と 3（既決着チェック）を**済ませてから**、自明かどうかを判定する。タイポ修正など機械的で自明な指摘は検証後そのまま適用してよいが、命名・設計・方針・a11y・規約など判断を伴う指摘は、前提検証と既決着チェックを踏まえた妥当性評価（判断と根拠）をユーザーに提示し、合意を得てから修正に着手する。
5. Edit で修正を適用する。指摘箇所だけでなく、同じテスト・関数内のテストデータや検証内容の整合性も確認する。
6. 全コメントの修正が完了したら、プロジェクトの lint コマンドと test コマンドを実行する。
   - コマンドはプロジェクトの CLAUDE.md や package.json / Makefile 等から判断する。
   - lint → test の順に実行し、両方パスすることを確認する。
7. lint/test が失敗した場合は修正し、再度実行する。

## Phase 3: コミットとプッシュ

1. 修正したファイルをステージングする（変更ファイルを明示的に指定）。
2. コミットメッセージはプロジェクトの規約に従う。
3. プッシュする。

## Phase 4: コメントへの返信

1. PR本文から署名を抽出する:
   ```bash
   gh pr view --json body --jq '.body' | grep -B1 -A3 -E '🤖|Generated with|Co-Authored-By'
   ```
   - 署名は本文末尾とは限らないため、固定行数の切り出し（`tail -N` 等）ではなくパターン検索で抽出する（例: `🤖 Generated with [Claude Code](https://claude.com/claude-code)`）。
   - 見つからない場合は**必ずユーザーに確認する**。スコープ外でスキップする指示があっても署名確認は省略しない。

2. **返信文面は投稿前に全文をユーザーに提示し、合意を得てから投稿する**。フロー合意は文面合意ではないため。

3. 各コメントに返信する。インラインコメントはスレッド返信、issue コメント・レビュー本文への返信はスレッド返信 API が無いため新規 issue コメントで返す（どの指摘への返信か冒頭で分かるようにする）:
   ```bash
   # インラインコメントへの返信
   gh api repos/{owner}/{repo}/pulls/{number}/comments/{comment_id}/replies \
     -X POST -f body="<対応内容の簡潔な説明>

   <署名>"
   # issue コメント・レビュー本文への返信
   gh api repos/{owner}/{repo}/issues/{number}/comments \
     -X POST -f body="<対応内容の簡潔な説明>

   <署名>"
   ```
   - 返信本文は対応内容を1〜2文で簡潔に記載する。
   - AI レビュアー（Copilot 等）への返信はお礼・挨拶は入れず、事実と判断理由のみ書く。人間のレビュアーへの返信には通常の敬語・お礼を入れる。
   - **返信に書く事実は一次情報で確認済みのものだけにする。** 他リポの慣例・前提条件・コードの挙動などを根拠に挙げるときは、断定する前に裏取りする（スコープ外/対応不要と返す場合の根拠も例外ではない）。未確認の推測を断定形で書かない。
   - 対応したコミットハッシュ（短縮形）を含める。**ASCII 境界 (スペース+括弧) で囲む**: `〜しました (daea499)。` の形式にする。日本語句読点 (`。` `、`) と直結すると GitHub のオートリンクが効かないため、必ず ASCII の括弧やスペースで挟む。
   - 末尾に空行 + 署名を付ける。

4. 投稿後、実際の反映内容を取得して確認する。body の変数展開・引用崩れ等で意図と異なる内容が投稿されても、POST の成功応答からは検出できないため:
   ```bash
   gh api repos/{owner}/{repo}/pulls/comments/{reply_id} --jq '.body'
   ```

## Phase 5: PR 本文見直し

1. 対応で加わった変更（振る舞い変更、スコープ拡張、テスト件数増減など）が PR 本文の Summary / Test plan に反映されているか確認し、必要なら `gh pr edit {number} --body-file <file>` で更新する。
2. **本文中の検証可能な記述（変更ファイル一覧・行数・件数等）は、触らない箇所も含めて `gh pr view --json files` / `git diff --stat` で実態と突合する**。自分が編集する本文に未検証の記述を残すと、食い違いが自分の主張として通ってしまうため。
3. 更新後、反映された本文を再取得して確認する。

## Phase 6: 完了前の最終確認

振り返りに入る前に、Phase 1 の 3 ソースを再取得し、未対応の指摘が残っていないことを確認する。対応中の新着と Phase 1 の取りこぼしをここで捕捉し、見つかったら Phase 2 に戻る。

## Phase 7: 振り返り — 指摘の根本原因と再発防止

全コメントへの対応・返信が完了したら、指摘を俯瞰して「なぜ見落としたか」を分析する。

1. 指摘を根本原因のパターンで分類する（例: 利用コンテキストの未確認、削除後の参照残り、戦略の不統一、仕様の見落とし等）
2. 各パターンについて「実装時にどのチェックをしていれば防げたか」を具体的に言語化する
3. 再発防止策として、防止策を反映すべきスキルとその変更内容を具体的に提案する（このスキル自体も対象）

**出力フォーマット:**

```
## 振り返り

| パターン | 該当指摘 | 防止策 | 反映先スキル |
|----------|---------|--------|-------------|
| <根本原因> | #1, #3 | <実装時に何を確認すべきだったか> | <スキル名と追加内容> |
```

- 指摘が1件だけでも省略しない
- 既にスキルに組み込み済みの観点であれば「対応済み」と記載する
- ユーザーが不要と判断すればスキップしてよい
- **各セルは1行で収める。** Claude Code の表レンダラーは `<br>` や行末2スペースを含むあらゆるセル内改行をサポートしない (GitHub issue #26390)
- 書ききれない詳細は表の下に箇条書きで補足する

## 注意事項

- 対応不要と判断したコメントはスキップ理由をユーザーに説明し、確認を取る。
- 返信はすべてのコメントに対して並列で送信してよい。
